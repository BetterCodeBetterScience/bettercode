# Reproducible LaTeX Listings — Design

**Status:** Draft for review
**Date:** 2026-05-27
**Scope:** `latex/book-testing.tex` (158 `lstlisting` blocks)
**Author:** Russell Poldrack (with Claude Code)

## Problem

The book's LaTeX sources embed code samples and program outputs as hand-curated `lstlisting` blocks. The embedded code drifts from the canonical implementations in `src/bettercode/`, and the embedded outputs (pytest sessions, REPL transcripts) cannot be regenerated — so it is not possible to confirm that what the book shows still corresponds to what the code does.

We want a build-time system where the LaTeX pulls code and outputs from canonical, runnable sources rather than hard-coding them, and where a verification step in the build fails if the rendered book would not match reality.

## Goals

1. Every non-trivial code block in `book-testing.tex` resolves to a runnable canonical file.
2. Every shell/REPL output block is generated by actually running a command and capturing the result.
3. The build hard-fails if committed outputs no longer match what the code produces.
4. The author iterates on a single block (`--only <id>`) without rebuilding everything.
5. The design extends cleanly to subsequent chapters with no changes to the build tooling itself.

## Non-goals

- Converting chapters other than `book-testing.tex` in this effort.
- Eliminating every inline `lstlisting` (tiny syntax-only patterns may stay inline).
- Rewriting the rendered book's narrative or restructuring chapters.

## Architectural decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Inject code/output into LaTeX via `\lstinputlisting` against canonical files | Single source of truth; canonical code is real, runnable, and verified. |
| 2 | One snippet file per pedagogical version, under `src/bettercode/testing/` | Explicit, easy to grep, no clever extraction tooling needed. |
| 3 | Generated outputs committed to git under `latex/generated/testing/` | PDF build never requires running Python; drift is visible in PRs. |
| 4 | Per-chapter YAML manifest declares (command → output_file → normalizers) | Single contract per chapter; LaTeX never embeds dynamic content directly. |
| 5 | Run real commands + apply named normalizers | Most faithful to what readers will see when they run the code. |
| 6 | Keep tiny syntax-only blocks (`Pythonshort`) as inline `lstlisting` | Avoids one-line files for content that has no execution semantics. |
| 7 | Use standard Python REPL (`>>>`) instead of IPython (`In :`/`Out:`) | Stable output, no IPython dependency, more universal. Pedagogical content change. |
| 8 | Hard-fail PDF build on listing drift | Strongest guarantee that the rendered book matches reality. |
| 9 | Migrate existing testing-chapter modules into `src/bettercode/testing/` | Safe — confirmed no external (notebook / sibling `example-*`) importers. |

In `book-testing.tex`, every block becomes one of:
- `\lstinputlisting[style=Python]{../src/bettercode/testing/escape_velocity_v1.py}`

## Manifest schema

One YAML file per chapter at `latex/manifests/<chapter>.yaml`. Single source of truth for what runs and where the result lands.

```yaml
chapter: testing
outputs:
  - id: pytest_escape_velocity_pass
    description: "Passing pytest output for test_escape_velocity"
    command: ["uv", "run", "pytest",
              "tests/testing_chapter/test_escape_velocity.py::test_escape_velocity"]
    cwd: "."                                  # repo root
    output_file: "latex/generated/testing/pytest_escape_velocity_pass.txt"
    expected_exit_code: 0
    normalize: [pytest_timings, file_paths, terminal_width]

  - id: pytest_escape_velocity_typo_fail
    description: "Failing pytest output when ev_expected has a typo"
    command: ["uv", "run", "pytest",
              "tests/testing_chapter/test_escape_velocity_typo.py"]
    output_file: "latex/generated/testing/pytest_escape_velocity_typo_fail.txt"
    expected_exit_code: 1
    normalize: [pytest_timings, file_paths, memory_addresses, terminal_width]

  - id: repl_floating_point_allclose
    description: "REPL demonstrating np.allclose for floating-point comparison"
    driver: "scripts/repl_drivers/testing/floating_point_allclose.py"
    output_file: "latex/generated/testing/repl_floating_point_allclose.txt"
    expected_exit_code: 0
    normalize: []
```

**Properties:**
- Either `command` (raw subprocess) or `driver` (Python script that prints the REPL transcript) — never both.
- `expected_exit_code` is explicit so demos that fail on purpose don't break the build.
- `normalize` is an ordered list of named filters from `scripts/normalize_output.py`.
- LaTeX references outputs by `output_file` path; there is no id-to-path lookup in the `.tex`.

## Build script

`scripts/build_listings.py` is a small CLI (~150 lines across three modules: `build_listings.py`, `manifest.py`, `normalize.py`).

```bash
# Regenerate all outputs for a chapter
uv run python scripts/build_listings.py build testing

# Regenerate one output
uv run python scripts/build_listings.py build testing --only pytest_escape_velocity_pass

# Verify committed outputs match what would be regenerated; exit 1 on drift
uv run python scripts/build_listings.py verify testing
```

For each manifest entry the script:
1. Runs `command` (or `driver`) via `subprocess.run`, capturing combined stdout+stderr.
2. Asserts exit code matches `expected_exit_code`; fails loudly otherwise.
3. Applies the listed normalizers in order.
4. In `build` mode: writes to `output_file`. In `verify` mode: diffs against committed file; reports unified diff on mismatch with the exact regenerate command.

## Normalizers

Pure `str -> str` functions registered by name. Initial set:

| Name | Effect |
|------|--------|
| `pytest_timings` | `1 passed in 0.10s` → `1 passed in X.XXs` |
| `file_paths` | Strip absolute paths to repo-relative |
| `memory_addresses` | `0x101403370` → `0xADDR` |
| `terminal_width` | Re-wrap `===` rule lines to a fixed width (e.g., 64 cols) |
| `temp_paths` | `/var/folders/.../tmp...` → `/tmp/...` |

Each normalizer is one function plus its unit test in `tests/test_listings_infra/test_normalize.py`. Adding a new one is a local change.

## REPL transcript generation

REPL blocks are generated by driver scripts that use `code.InteractiveConsole` (stdlib) via a shared helper:

```python
# scripts/repl_console.py — sketch
class Session:
    def __init__(self): ...
    def run(self, source: str) -> None:
        """Feed `source` to an InteractiveConsole; print the source prefixed
        with `>>>` (or `... ` for continuations), and any output or formatted
        traceback that resulted."""

# scripts/repl_drivers/testing/floating_point_allclose.py
from repl_console import Session
s = Session()
s.run("import numpy as np")
s.run("np.allclose(0.1 + 0.2, 0.3)")
```

Produces:
```
>>> import numpy as np
>>> np.allclose(0.1 + 0.2, 0.3)
True
```

- No IPython dependency.
- No cell numbers; tracebacks report `File "<stdin>"`.
- Tracebacks into snippet files reference real line numbers in committed
  `src/bettercode/testing/*.py` — stable unless those files are reformatted,
  in which case `verify` catches the drift on the next CI run.

**This is a content change to the book.** Every existing `In :`/`Out:` block becomes `>>>`/result. The chapter intro (or preface) gains a sentence stating that examples use the standard Python REPL. The `repl` style in `designchanges.sty` may need a visual tweak; verify during step 10 of the migration.

## Cross-block context and shared state

Many code blocks in the book depend on context established in earlier blocks (a function defined a few blocks back, an `import` from earlier in the session, a value from a prior REPL line). The model handles this through three explicit patterns:

**Pattern 1 — Function + test across two files.** The most common case in the testing chapter. The book shows a function in one block and a test that calls it in the next. These map to two canonical files (`src/bettercode/testing/<concept>_vN.py` and `tests/testing_chapter/test_<concept>.py`). The test file does a real `import` of the function; LaTeX pulls each block from its own file. There is no shared in-memory state — execution always re-imports — so the dependency is explicit and verifiable.

**Pattern 2 — One file, multiple LaTeX blocks via line ranges.** When the book shows one coherent piece of code interrupted by prose, use one runnable file and multiple `\lstinputlisting` calls with `firstline=…, lastline=…`. The file as a whole is the runnable unit; the book carves it up visually.

```latex
\lstinputlisting[style=Python, firstline=1,  lastline=10]{../src/bettercode/testing/foo.py}
% ... prose ...
\lstinputlisting[style=Python, firstline=11, lastline=25]{../src/bettercode/testing/foo.py}
```

**Pattern 3 — REPL session shown as multiple blocks.** Three options, in preference order:
- **3a (preferred):** Each visual block is its own driver script that does whatever setup it needs (re-import, redefine). Cheap, isolated, each block independently regenerable. Small redundancy across driver scripts, but invisible to the reader.
- **3b:** One driver produces one long transcript file; LaTeX uses `firstline/lastline` to display slices. Single source of truth for the session, but slice boundaries are fragile when prose moves around.
- **3c:** Single driver, single file — when the book actually shows one continuous block.

**Cross-chapter references.** Same as Pattern 1: the canonical file does a real `import` from another chapter's module. The book either shows the import (truthful) or hides it via `firstline=2` (cosmetic). Either way, the dependency is real and the build verifies it.

**Pedagogical-vs-canonical mismatch in imports.** The book sometimes shows imports the canonical library file does not need (e.g., the `escape_velocity` block shows `import numpy as np` because the test uses it). Three valid handling strategies, decided case-by-case during migration step 1:
1. Hide leading imports in the book via `firstline=N`; show them in the test block where they are actually used.
2. Add a "pedagogical preamble" file per block group that bundles imports plus the function as one runnable unit.
3. Lightly edit the book's narrative so imports appear where the canonical files put them.

Record the rule chosen for each block in `CONVERSION_NOTES.md`. Step 1's catalog will surface how often this comes up and whether a fourth pattern emerges that needs explicit design treatment.

## Workflow

**Author edits a block:**
```bash
# Edit src/bettercode/testing/escape_velocity_v1.py
uv run python scripts/build_listings.py build testing --only pytest_escape_velocity_pass
cd latex && make
```

**Full chapter regen:**
```bash
uv run python scripts/build_listings.py build testing
```

**Makefile additions (`latex/Makefile`):**
```makefile
listings:
	cd .. && uv run python scripts/build_listings.py build testing

verify-listings:
	cd .. && uv run python scripts/build_listings.py verify testing

pdf: verify-listings
	# existing latexmk/xelatex command — hard-fails on drift

pdf-no-verify:
	# escape hatch for prose-only iteration; no verification step
```

`pdf` is gated on `verify-listings` so any drift between committed outputs and what the code would produce blocks the build.

## CI

`.github/workflows/verify-listings.yml`:
- Triggers on pushes/PRs touching `latex/**`, `src/bettercode/testing/**`, `tests/testing_chapter/**`, `scripts/**`, or `latex/manifests/**`.
- `uv sync` → `uv run python scripts/build_listings.py verify testing`.
- On failure, surfaces the unified diff as a check annotation.

## Migration plan (testing chapter)

1. **Catalog every `lstlisting`** in `book-testing.tex` (158 blocks). Classify as `code` / `output` / `inline-keep`. Record in `latex/CONVERSION_NOTES.md`.
2. **Pre-check imports** — re-run grep over `notebooks/` and `../example-*/` for every module about to be moved. (Confirmed safe for testing-chapter modules as of 2026-05-27.)
3. **Create per-version snippet files** under `src/bettercode/testing/`. Naming: `<concept>_v<N>[_<short_descriptor>].py`.
4. **Migrate tests** to `tests/testing_chapter/`; update imports. Add intentionally-failing test files for failure-demo blocks.
5. **Write REPL drivers** under `scripts/repl_drivers/testing/` using the shared `repl_console.py` helper.
6. **Write `latex/manifests/testing.yaml`** — one entry per output file, grouped conceptually.
7. **Build the infrastructure** — `build_listings.py`, `normalize_output.py`, `repl_console.py`, plus unit tests in `tests/test_listings_infra/`.
8. **Run `build_listings.py build testing`** once to populate `latex/generated/testing/`. Commit the outputs.
9. **Rewrite `book-testing.tex`** block by block — replace inline `lstlisting`s with `\lstinputlisting` references (or keep inline for syntax-only blocks).
10. **Verify end-to-end**: `make verify-listings && make pdf`. Visually diff rendered PDF against the prior version. Tweak normalizers / `lstinputlisting` options (`firstline`, `lastline`, `breaklines`) for any block that renders poorly.
11. **Maintain `latex/CONVERSION_NOTES.md`** throughout — surprises, decisions, patterns. Raw material for the future skill.

## Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Rendered PDF line-wrapping differs from hand-curated blocks | Per-file `lstinputlisting` options; expected friction in step 10. |
| External importer overlooked during migration | Step 2 pre-check + a CI smoke test that imports every chapter module. |
| Pytest output order varies across runs | Pin each output to a specific `pytest <file>::<test>` invocation; no broad collection. |
| Traceback line numbers drift when snippet files are reformatted | `verify` catches the drift; author regenerates. |
| Author bypasses `verify` locally and pushes stale outputs | CI runs the same `verify` step on PR; blocks merge. |
| YAML manifest grows unwieldy as more chapters are added | Per-chapter sharding; `--only <id>` for fast iteration. |
| Inter-block dependencies (function defined in block A, used in block B) | Covered by the three patterns in "Cross-block context and shared state". Step-1 catalog surfaces frequency and any fourth pattern. |
| Book shows imports the canonical file doesn't need (or vice versa) | Decide per-block during migration (hide via line range, add preamble file, or edit prose). Rules recorded in CONVERSION_NOTES.md. |

## Extensibility

Adding a new chapter requires only:
1. `src/bettercode/<chapter>/` with per-version files.
2. `tests/<chapter>/` with featured tests.
3. `latex/manifests/<chapter>.yaml`.
4. Rewrite `book-<chapter>.tex` lstlistings.

The build script, normalizers, and REPL helper are reused as-is. New normalizers are added as named functions plus tests.

**Caveat for future chapters:** several modules used by other chapters *are* imported externally (`bettercode.simple_workflow`, `bettercode.rnaseq.stateless_workflow.execution_log`, `bettercode.database_example_funcs`, `bettercode.database`, `bettercode.taxi_utils`, `bettercode.penguindata`, `bettercode.llm_utils`). For those chapters, the "rename-in-place" migration step is not safe. Choose one of:
- Keep the top-level module in place AND treat the chapter-local file as a copy/re-export, or
- Update the external importers in the same change.

**Non-Python content types are handled for free.** `\lstinputlisting` is content-agnostic, so future `R`, `Dockerfile`, `Makefile`, `yaml`, `toml`, `json`, and `transcript` blocks can be referenced from text files alongside the chapter — no manifest entry needed unless they need to be executed to produce a result.
